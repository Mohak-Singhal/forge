  3. Architecture on TrueForge

    Forge is Cline with its agent loop replaced by TrueForge (trueforge local mode, npx @truefoundry/trueforge@latest, never deployed). The extension never calls a model provider; TrueForge owns the loop, the model, approvals and streaming.

    Extension ↔ TrueForge. The extension creates a TrueForge session per task and sends turns through the TrueForge TypeScript SDK (client.ts → SdkSessionHost), rendering streamed events in the Cline webview. The agent definition is committed at .trueforge/agents/forge-editor.json: instructions, primary model, preloaded editor tools, and per-tool approval policy.

    Editor capabilities as MCP tools (loopback HTTP server, 127.0.0.1:8791, stateless Streamable-HTTP — fresh server+transport per request; auto-registered with TrueForge at boot as the vscode-editor-tools connector):

    ToolPurposeApproval
    editor_read_fileread file (1-based line range)auto
    editor_searchregex search over workspace → path:lineauto
    editor_repo_mapdef/class signature map of the repoauto
    editor_retrieveBM25 retrieval of code chunks (strategy in §4)auto
    editor_diagnosticsfast Python syntax check (py_compile)auto
    editor_propose_editstage multi-hunk edits; nothing writes before user accepts the diffTF-gated
    editor_run_commandworkspace shell (destructive/network commands refused)TF-gated
    editor_undo_last_editrestore exact pre-edit bytes of the latest applied proposal (or a named proposalId)TF-gated

    Approval → review flow. TrueForge pauses on tool.approval_required for gated tools; the extension maps that to Cline's Approve/Reject buttons; only on allow does the MCP tool stage/apply. The rejected hunks never hit disk (verified: staging a stale-base hunk leaves file bytes identical). Applied edits carry their byte pre-image (undoSnapshots), so undo is exact.

    Harness features used, and why. (i) Preloaded tools — deferred tool discovery made the model call an unmapped read on the first run; preloading the editor tools fixed it at the harness, not in the model. (ii) Compaction (context_management.compaction) for long runs. (iii) dynamic_sub_agents and ask_user_questions enabled. (iv) iteration_limit 80. (v) Streaming + cancellation ride the SDK cancel path (see A3).

  4. How context is selected

    Strategy. The agent never receives whole files up front. It starts from a repo map (path + def/class signatures), then calls editor_retrieve with the task text: BM25 over workspace chunks (approx. 1,000-token windows, 100-token overlap, skip list for node_modules/.venv/dist), top-k=6 by score (default), each hit returned with path:startLine-endLine (score N.NN) so the agent — and the judge in the TrueForge session view — sees which chunks were selected and why. Explicit @file mentions are honoured as ground truth (the agent still retrieves cross-cutting context). Budget: 6 chunks ≈ 4.5K tokens of retrieved context; agent then reads exact ranges with editor_read_file.

    Why this works on a 17K-line repo. BM25 is lexical (no embedding API, no ToS cost, deterministic); signatures in the repo map give global orientation; the agent showed the selection live in Task B: repo_map → retrieve (tests/test_cli.py, score 69.02) → search (cli.py) → read_file, then proposed edits to three unnamed files (src/flask/cli.py, tests/test_cli.py, docs) plus docs/api.rst. No file names were given by the user in Task B.

    Rejected alternatives. Whole-file concatenation (window blow-out), embedding RAG (provider dependency — violates "model in TrueForge only"), and LSP symbols only (too coarse for behaviour). BM25 was chosen for determinism and zero external dependency.

No API key is committed to this repo; the provider key lives only in the TrueForge server's config (see .trueforge/models.example.json for importable Ollama/gateway examples). The extension never sets or reads the provider. To switch models: open TrueForge Settings → Models, add your provider, then change model.name in .trueforge/agents/forge-editor.json (or pick the model in the TrueForge UI/session) and reload — works with any model TrueForge is configured with, any provider.

    Task C note. With the provider pointed at an unreachable endpoint, the harness fails in ~2s with a clear message — see §3 and the video. The second model is configured but TrueForge's free-gateway failover does not engage on transport failure for this provider shape; the clear-message path is what we demonstrate.

  8. Known limitations & what we'd do with another month

    • Undo granularity. editor_undo_last_edit is byte-exact but LIFO: it restores the most recent applied proposal wholesale, including hunks overlapping later manual edits. Another month: per-hunk undo replay against the working tree.
    • Fallback never promoted. With an unreachable primary, TrueForge returned a clear error instead of silently switching to jev-113-free; we'd pursue TF provider-level failover config (or a tiny "retry once against the fallback" option in the agent) with the evaluation team.
    • Approval buttons rely on the webview. After window reloads the composer can appear unresponsive until the webview re-renders (observed in CUA); fix: re-render trigger on window focus.
    • Loopback MCP has no auth (127.0.0.1 only, TF egress allowlist). Fine for local single-user demos; not for shared machines.
    • execFile silently lost its callback across the Streamable-HTTP flush boundary in the Electron utility process (found via SSE probes; fixed by rewriting editor_run_command on spawn). Some latent fragility may remain in other long-lived promises.
    • No checkpoints in TF local mode. Upstream Cline checkpoints don't cover our apply path; the undo tool is the revert. With more time: wire the harness's snapshot API.
    • Task B's test only asserts key-family masking, not order/duplicates; docs (cli.rst prose) not sphinx-built here.
    • Dev-host windows were killed repeatedly by the local automation environment — a test-harness concern, not the extension; recorded once in the demo flow workaround (relaunch + continue).
